Web

Web Security

Companion page: pages/12-security.html

This deck is self-contained — every slide explains its concept end-to-end so it's readable without the lecturer's narration.

It's illegal

Probing the security of a website without the owner's explicit permission is a crime in most jurisdictions, even if you don't actually do anything malicious — even if you only "look."

In the US, the Computer Fraud and Abuse Act carries penalties up to 20 years in prison and applies to non-US citizens. In Switzerland, Art. 143bis CP is the equivalent offense ("unauthorized access to a data processing system").

If you want to practice on real systems, go on a Bug Bounty program (HackerOne, Bugcrowd, Intigriti) where the owner has given written authorization to test specific scopes in exchange for disclosure.

Key points
  • No site is fair game without written authorization
  • "Just curious" doesn't hold up legally
  • Bug bounty programs are the legitimate practice ground

Threat map — three layers

A web application stretches across three physical layers, and each layer is its own attack surface with its own defenders. The browser layer is constrained by what the platform enforces (SOP, CORS). The network layer is mostly about transport security (HTTPS / HSTS). The server layer is where YOUR code runs and where the attacker is least constrained — they can send any bytes to any endpoint.

BrowserNetworkServer
SOP, XSS, CSRF, phishing, variable injectionCORS (browser-enforced), HTTPS, HSTS, eavesdroppingSQL injection, SSRF, info leaks, supply chain, weak password storage, rate limiting

A recurring principle: the security model lives at the boundaries. Once an attacker is past a boundary, the inner layer doesn't get to second-guess them. So defense in depth means every boundary takes its job seriously.

§1

Same-Origin Policy — the rule

The Same-Origin Policy says two pages from different origins should not be able to interfere with each other. This is the foundational rule that makes it safe to have multiple tabs open at once — your banking tab and an attacker's tab can coexist without the attacker reading your bank's data.

An origin is the triple (protocol, host, port). Two URLs are same-origin only if all three match. Default ports (80 for http, 443 for https) are implicit.

Page APage BSame origin?
http://a.comhttps://a.comNo — protocol differs
https://a.comhttps://a.com:8443No — port differs
https://a.comhttps://api.a.comNo — host differs (subdomain counts!)
https://a.comhttps://a.com:443Yes — 443 is the default port for https
§2

SOP — what's blocked and what's allowed

The Same-Origin Policy is most concrete when you list what it actually blocks. Three categories of cross-origin interaction are forbidden:

  • Reading or modifying the DOM of another page (e.g. via an iframe's contentDocument)
  • Reading the response body of a cross-origin fetch
  • Reading another origin's cookies, localStorage, or IndexedDB

Some cross-origin interactions remain allowed because the web platform depends on them — they were grandfathered in from before SOP existed:

  • Embedded static resources: <img>, <script>, <link rel="stylesheet">
  • Submitting a form with action pointing to another origin
  • Explicit, opt-in mechanisms: postMessage for iframe comms, CORS for fetch
§2

Cross-origin iframe communication

When you embed an iframe from a different origin, the SOP blocks direct DOM access in both directions. The legitimate channel is postMessage: an explicit message-passing API where both sides choose to communicate.

// Parent at parent.example.com — send a message
iframe.contentWindow.postMessage(msg, "https://child.example.com");

// Child at child.example.com — receive it
window.addEventListener("message", (event) => {
  if (event.origin !== "https://parent.example.com") return;
  // safe to use event.data
});

The two security rules that matter: the sender must always pass a specific targetOrigin (never "*" for sensitive data — that delivers your message to whoever happens to have loaded the iframe), and the receiver must always verify event.origin before trusting event.data.

§2

CORS — Cross-Origin Resource Sharing

The Same-Origin Policy blocks most cross-origin fetch by default. CORS (Cross-Origin Resource Sharing) is the opt-in mechanism that lets a server selectively allow them. Without CORS headers in the response, the browser hides the response body from your JS — even if the request itself succeeded and the server processed it.

This is enforced by the browser, not the server. The request still reaches the network, and any side effects on the server still happen. CORS protects the user's data (the response body) from being read by hostile JS in a tab they didn't initiate. It does NOT protect your server from unwanted requests — for that, you need real authentication and CSRF tokens.

// Response from api.com:
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.com
§3

CORS — preflight requests

For non-simple requests (PUT/DELETE, requests with Content-Type: application/json, or custom headers), the browser refuses to send the real request until it gets server permission. It sends a preflight: an OPTIONS request asking "may I do this?"

OPTIONS /api/account HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: X-Auth, Content-Type

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: DELETE, GET
Access-Control-Allow-Headers: X-Auth, Content-Type
Access-Control-Max-Age: 600

Only after the server responds with the allow-list does the browser send the actual DELETE. This is the only browser-enforced check that prevents some classes of cross-origin abuse — but simple GET/POST with form-encoded bodies skip the preflight entirely.

§3

CORS — credentialed requests

By default, cookies and HTTP auth are not sent on cross-origin fetch requests, and the server can't read them. To include them, you have to opt in on both sides.

// Client opts in
fetch("https://api.com/me", { credentials: "include" });

// Server opts in
Access-Control-Allow-Origin: https://app.com     // must be specific, not *
Access-Control-Allow-Credentials: true

The constraint that catches people: with credentials, Access-Control-Allow-Origin: * is invalid. The server must echo back the specific allowed origin. If either side forgets to opt in, the browser drops the response.

Key points
  • CORS is enforced by the browser, not the server
  • Preflight asks permission for non-simple methods
  • Credentials require both credentials: include AND server opt-in
§3

Cookies — anatomy

A cookie is a single key-value pair the server tells the browser to store. With every subsequent request to that origin, the browser sends all stored cookies back. Cookies are how stateful sessions work on top of HTTP's stateless protocol.

Set-Cookie: session_id=eyJhb...;
            Domain=example.com; Path=/;
            Max-Age=86400;
            Secure; HttpOnly; SameSite=Lax

The key-value pair is followed by attributes that the browser interprets. Domain and Path restrict which requests carry the cookie. Max-Age sets expiry (in seconds). Secure, HttpOnly, and SameSite are the security knobs.

§4

Cookie security attributes

Three attributes do most of the security work, and they each defend against a different threat:

  • Secure — cookie is only sent over HTTPS. Without it, a network eavesdropper on an HTTP request can steal the cookie.
  • HttpOnly — cookie is not readable from JavaScript (document.cookie can't see it). Mitigates session theft when an attacker gets code execution on your origin via XSS.
  • SameSite — controls whether the cookie is sent on cross-site requests. Three values:
    • Strict — never on cross-site requests, even when the user clicks a link from another site
    • Lax — sent on top-level GET navigation; blocked on cross-site POST and embedded subresources (this is the modern browser default since Chrome 80, 2020)
    • None — sent on every cross-site request (requires Secure)
§4

Cookie name prefixes — __Host- and __Secure-

Modern browsers enforce stronger guarantees when a cookie name starts with one of two reserved prefixes. The browser refuses to set the cookie if the constraints aren't met — so the prefix is a self-enforcing tag.

  • __Secure-name — must be set with the Secure attribute (HTTPS only)
  • __Host-name — must be Secure, must have Path=/, must NOT have a Domain attribute. The cookie is bound to that exact host, so a subdomain can't set or override it.
Set-Cookie: __Host-session=eyJ...;
            Secure; HttpOnly; SameSite=Lax;
            Path=/

For session cookies, __Host- is the best choice — it eliminates an entire class of subdomain-takeover attacks at the platform layer.

§4

Sessions

A session ID is a server-issued random secret, sent to the client in a cookie. The server keeps the corresponding state (which user is logged in, what's in their cart) in memory or a database. The cookie just identifies which row to look up.

If an attacker steals your session ID, they ARE you for as long as it's valid — they don't need your password, they can't be challenged for 2FA, they just use your session. So the bar for handling session IDs is high:

  • Generate from a cryptographically secure RNG (Node: crypto.randomBytes(32)). Never sequential, never predictable.
  • Set Secure; HttpOnly; SameSite=Lax and use the __Host- prefix
  • Rotate the session ID on login and on privilege escalation (prevents session fixation)
  • Expire idle sessions server-side, not just by the cookie's Max-Age — an old leaked cookie must stop working
§4

CSRF — Cross-Site Request Forgery

Browsers send cookies along with every request to their origin, regardless of who triggered the request. CSRF abuses this: a malicious page tricks the user's browser into firing an authenticated request to a target site where the user is already logged in.

<!-- on evil.com -->
<form action="https://bank.com/transfer" method="POST">
  <input type="hidden" name="to"     value="attacker">
  <input type="hidden" name="amount" value="1000">
  <input type="submit" value="Click here to win a free iPad!">
</form>
<script>document.forms[0].submit();</script>

The browser sends the user's bank.com session cookie along with the POST. If the bank's transfer endpoint trusts the session cookie alone, the transfer succeeds. Pre-2020 this was an everyday bug.

§5

CSRF — the modern default

Since Chrome 80 (Feb 2020), browsers default cookies without an explicit SameSite to SameSite=Lax. That alone closes the classic CSRF attack on POST requests — the cookie simply isn't sent on a cross-site POST. Naked CSRF is no longer an everyday bug.

But the default is not a panacea. Top-level GET navigation still ships the cookie under Lax — so if your endpoint takes destructive action on GET (it shouldn't), you remain exposed. And not every browser is modern enough; older browsers, intranet zones, and some embedded webviews need additional defense.

Key points
  • SameSite=Lax default closes cross-site POST CSRF
  • Top-level GET still ships the cookie
  • Never put state changes on GET, even when "small"
§5

CSRF — defense in depth with tokens

For sites that need to work in older browsers, that support third-party embeds, or that can't rely on SameSite=Lax everywhere, the time-tested defense is a CSRF token. The server generates a per-session secret and embeds it in every form as a hidden input. The server rejects state-changing requests unless the submitted token matches.

<form action="https://bank.com/transfer" method="POST">
  <input type="number" name="amount" value="1000">
  <input type="hidden" name="csrf"
         value="eyJ2IjoxLCJldSI6MCwic3QiOjB9">
  <input type="submit" value="Send">
</form>

An attacker on another origin can't read the token (the Same-Origin Policy blocks them from reading the form), and the token is too long to guess. A stateless variant called double-submit cookie sends the same random value as both a cookie AND a request header, and the server checks they match — no server-side storage needed.

Important: CSRF tokens do NOT protect against XSS. Once attacker JS runs on your origin, it can simply read the token from the page and use it.

§5

XSS — Cross-Site Scripting

Cross-Site Scripting is a code-injection vulnerability where untrusted user data unexpectedly becomes executable code on a victim's browser. The injected code runs with the victim's origin and session — it can read their data, perform actions on their behalf, exfiltrate cookies, anything the legitimate page could do.

XSS is the single most common web vulnerability in study after study. The defenses are well-understood but easy to get wrong because they're context-dependent — what's safe in one place is dangerous in another.

There are three classic flavors:

  • Reflected — attacker crafts a URL whose query string is included unescaped in the server's response. Victim clicks the link, runs the code. One click, one victim.
  • Stored — attacker submits content (a comment, profile field) that the server stores and later serves to other users unescaped. Every viewer is a victim.
  • DOM-based — vulnerable client-side JS reads untrusted input (URL, postMessage, fragment) and writes it into the DOM as code. No server involvement.
§6

XSS — a reflected example

Consider a server that reflects a query parameter into the response without escaping:

// Server:
app.get('/', (req, res) =>
  res.send(`<h1>Hello, ${req.query.user}</h1>`))

// Attacker sends victim a URL:
https://target.com/?user=<img src=x onerror=alert(document.cookie)>

The browser receives <h1>Hello, <img src=x onerror=alert(document.cookie)></h1>, fails to load the bogus image source, and runs the onerror handler — exfiltrating the victim's cookies to the attacker.

A common confusion: innerHTML refuses to execute <script> tags inserted at runtime, so developers think it's safe. But the onerror / onload trick works on any element type — <img>, <svg>, <iframe> — and bypasses that intuition.

§6

XSS defense 1 — escape on the way out

The first line of defense is to escape user input at output time, with rules specific to the context where the data lands. Different parts of an HTML document need different escaping:

  • Element body: escape < and &
  • Attribute value (quoted): escape ", ', and &
  • URL attribute (href, src): also URL-validate (no javascript: scheme)
  • JS string: don't — there is no safe escaping into a <script> block. Route the data through an HTML container and parse it client-side.

The right answer is to use a template engine that does context-aware escaping for you: EJS's <%= %>, React's {}, Vue's {{ }}, etc. Never hand-concatenate user input into HTML strings — that's where the bugs live.

§6

XSS defense 2 — Content Security Policy

Even with diligent escaping, mistakes happen. CSP is a defense layer that restricts what scripts the browser will execute — so even if an attacker injects something, it doesn't run. Modern best practice uses nonces: every legitimate <script> tag carries a per-response random token, and the browser refuses to run any inline script that doesn't have it.

Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m';
  object-src 'none';
  base-uri 'self';
<script nonce="r4nd0m">
  // legitimate inline JS, runs because the nonce matches
</script>

An injected <script> tag from a payload doesn't know the nonce (which changes per response), so the browser refuses to execute it. Same for inline event handlers — the policy blocks them by default.

§6

XSS defense 3 — Trusted Types

Trusted Types (Chromium-stable, available in Chrome and Edge) is a structural fix for DOM-based XSS. With the policy enabled, the dangerous DOM sinks — innerHTML, setTimeout(string), eval, document.write, and others — refuse to consume raw strings. They only accept "trusted" objects produced by a registered sanitizer policy.

Content-Security-Policy:
  require-trusted-types-for 'script';
  trusted-types my-policy;

With this in effect, el.innerHTML = userString throws a TypeError unless userString came from a registered sanitizer. You explicitly opt in to processing untrusted strings at well-defined boundaries, and everything else is structurally safe.

Defense in depth — assume XSS will land someday
  • HttpOnly on session cookies blocks JS theft
  • Re-auth for sensitive actions (password change, transfer)
  • Send confirmation emails for sensitive operations
§6

Phishing — IDN homographs

"Security solutions have a technological component, but security is fundamentally a people problem." — Bruce Schneier

Phishing tricks the user, not the code. The web platform offers attackers several primitives for impersonation. The classic one is the internationalized domain name (IDN) homograph: hostnames may contain Unicode characters, but DNS only understands ASCII — so they're encoded as "punycode."

https://www.аpple.com/

The а in that URL is Cyrillic U+0430, not Latin a. The browser sends xn--pple-43d.com to DNS — a completely different domain than apple.com. Modern browsers show the punycode form when a hostname mixes scripts suspiciously, but exact-script lookalikes and subdomain confusion (apple.com-login.evil.com) still slip past skimming users.

§7

Phishing — what actually helps

The honest answer is that user training, posters in the breakroom, and "always check the URL!" advice all have documented but modest effectiveness and decay quickly without reinforcement. The defenses that actually work move the verification into the platform:

  • Password managers bind credentials to domains and refuse to autofill on the wrong one. Even if the user is fooled visually, the manager isn't.
  • Hardware security keys / Passkeys go further — the browser binds the cryptographic signature to the relying-party's origin. A phishing site at раypal.com simply cannot ask the authenticator for a signature meant for paypal.com. It's structurally impossible, not "merely difficult."
  • Email security (SPF, DKIM, DMARC) reduces the surface of phishing email reaching the inbox.

The lesson: phishing is solved at the platform layer, not at the user-vigilance layer. We'll come back to passkeys when we talk about authentication.

§7

Server-side security — the model changes

On the server, the attacker is no longer constrained by the browser. They can send any bytes to any endpoint, bypass your UI entirely, replay requests, fuzz inputs, and use any tool they like. The browser-enforced rules (SOP, CORS) protect users from each other in the browser — they do nothing to protect your server from a direct attacker.

This means the server-side security model has to live in your code. Every endpoint validates input. Every database query treats user data as data, not code. Every cross-host fetch validates the target. Every error message considers what it might reveal.

We'll look at four classes: SQL injection, SSRF (Server-Side Request Forgery), information leaks, and supply-chain attacks. Plus the universal hygiene of rate limiting.

§8

SQL injection

The canonical server-side bug. When user input is concatenated directly into a SQL query string, an attacker can break out of the intended data context and inject query syntax.

// Vulnerable
db.query(`SELECT * FROM users
  WHERE name = '${user}' AND pass = '${pass}'`);

// Attacker sends:  user = admin' --
// Query becomes:
SELECT * FROM users WHERE name = 'admin' -- ' AND pass = '...'
//                                       ^^^ everything after ignored

The classic admin' -- trick uses the SQL line comment to strip the password check. With ' OR '1'='1 you don't even need to know any usernames — the WHERE clause becomes tautological and the query returns every row.

The fix is parameterized queries (a.k.a. prepared statements). The database driver sends the SQL and the values as separate things; the database substitutes safely. Attacker input can never become query syntax because it's never parsed as syntax.

// Safe
db.query('SELECT * FROM users WHERE name = $1', [user]);

An ORM (Prisma, Sequelize, Drizzle, …) does this for you and adds type safety. There's no reason to write raw concatenated SQL in 2026.

§8

SSRF — Server-Side Request Forgery

Your production server sits on the same network as services the public internet cannot reach: a cloud metadata service, an internal admin API, a database that only listens on a private IP. If your code fetches a URL from user input (image proxy, webhook delivery, URL preview, PDF rendering), the attacker can make YOUR server reach those internal targets.

// Attacker submits:
{ "avatar_url":
  "http://169.254.169.254/latest/meta-data/iam/security-credentials/" }

// Your code:
const img = await fetch(req.body.avatar_url);
// Your server obediently fetches AWS metadata — including
// short-term credentials with whatever role the box has.

SSRF was the root cause of the Capital One breach (2019). Defenses:

  • Allowlist hosts where possible (e.g. only fetch from cdn.example.com)
  • If users supply arbitrary URLs, resolve DNS yourself and verify the IP is public (not 127.0.0.1, 10.0.0.0/8, 169.254.0.0/16, …). Beware DNS rebinding — re-resolve and re-check before connecting.
  • Short connect timeouts. Don't follow redirects without re-validating.
§8

Supply chain + information leaks

A modern web app loads hundreds of transitive npm dependencies — any of which can be compromised. Three flavors:

  • Dependency confusion — attacker publishes a public package with the same name as your internal private one; your build picks the public one
  • Typosquatting — colorss instead of colors, nodemom instead of nodemon
  • Maintainer compromise — legitimate package gets a malicious update pushed (this has happened to widely-used packages multiple times in recent years)

Defenses: commit your lockfile, run npm audit / Dependabot / Renovate, avoid postinstall scripts where possible, prefer fewer direct dependencies.

Information leaks are the server giving up the breach without an active attack — stack traces in error responses, over-fetching (returning the full user object when the client needed a display name), or verbose errors revealing whether a username exists (the response-discrepancy pattern). Generic error messages and minimal API responses are the fix.

§8

Rate limiting

Most online attacks are mass-volume: credential stuffing tries millions of leaked passwords, scrapers try to download your entire user base, denial-of-wallet attacks against paid APIs run up your bills. The defense is universal: rate limit everything, per-IP and per-account.

  • Authentication endpoints: failed-login backoff, lockout after N attempts
  • Password reset and signup: prevent enumeration
  • Expensive read endpoints: per-account quotas
  • Anything that costs money on the backend (LLM calls, geocoding APIs, …): per-account limits

Rate limiting isn't glamour — it doesn't show up in OWASP Top 10 as its own item — but it's first-class defense, not a polish item. Most "advanced" attacks fail or are detectable when basic rate limits are in place.

§8

Storing passwords

Three rules, each defeating a specific attack class:

  • Hash, don't encrypt. Encryption is reversible — if your host is compromised, the key likely is too. Hashing is one-way: a leaked database doesn't give the attacker passwords directly.
  • Salt. Random per-user bytes, stored alongside the hash. Two users with the same password get different hashes; precomputed rainbow tables become useless.
  • Slow function. Use bcrypt, scrypt, or Argon2id — algorithms designed to be deliberately slow (~100ms per hash on production hardware). The user logs in once per day; the attacker brute-forcing the leak pays 100ms per guess. Tunable: bump the cost as hardware gets faster.

Use a library. Don't roll your own crypto. The implementations of bcrypt and Argon2 are battle-tested; the ways to subtly screw up a hand-written hash are many.

§9

Modern password rules — NIST SP 800-63B

The old advice (complex character classes, forced 90-day rotation, security questions) is now actively harmful. NIST's current guidance, widely adopted as industry consensus:

  • No mandatory periodic changes. Forced rotation pushes users toward weak, sequential passwords ("Spring2026!" → "Summer2026!"). Rotate only on suspected compromise.
  • No silly composition rules. Length beats complexity. Allow long passwords (minimum 64 chars), allow spaces, allow Unicode.
  • Block known-breached passwords. Check candidates against Have I Been Pwned's k-anonymity API at signup and password change. This is more effective than any composition rule.
  • Rate-limit and lock out failed attempts. Bcrypt cost helps against offline brute force; rate limiting helps against online brute force.
  • Never send passwords by email or SMS. Use one-time signed links instead.
  • 2FA / MFA on anything important. Prefer WebAuthn/Passkeys over TOTP over SMS.

§10

JWT — what's actually inside

A JSON Web Token is three base64url-encoded parts joined by dots: a header (algorithm and type), a payload (the claims), and a signature over the first two computed with a shared secret (HMAC) or a private key (RSA / EC).

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9     ← header   {"alg":"HS256","typ":"JWT"}
  .eyJzdWIiOiJhbGljZSIsInJvbGUiOiJ1c2VyIn0  ← payload  {"sub":"alice","role":"user"}
  .K7rL3pXq...                              ← signature

The payload is signed but readable — base64url is encoding, not encryption. Anyone with the token can decode the claims. Never put secrets in a JWT payload.

Classic foot-guns:

  • alg: "none" — some libraries historically accepted unsigned tokens. Always validate alg against an allowlist on the server.
  • Algorithm confusion — server uses HS256, attacker sends RS256 (or vice versa), tricks the library into validating with the wrong key. Pin the algorithm server-side.
  • Long TTLs without revocation — JWTs are stateless; you can't easily revoke one. Use short TTLs + a refresh mechanism.
§10

OAuth2 — Authorization Code with PKCE

OAuth2 lets a third-party app act on a user's behalf without seeing the user's credentials. For browser apps, the modern recommended flow is Authorization Code + PKCE ("Proof Key for Code Exchange"). Step by step:

  1. App generates a random code_verifier, hashes it with SHA-256, base64url-encodes → code_challenge
  2. App redirects user to GET /authorize?code_challenge=…&client_id=…&redirect_uri=…&state=…
  3. User logs in at the authorization server, consents
  4. Auth server redirects back to redirect_uri?code=AUTH_CODE&state=…
  5. App POSTs to the token endpoint with the original code_verifier: POST /token grant_type=authorization_code&code=AUTH_CODE&code_verifier=…
  6. Auth server hashes the verifier, checks against the challenge from step 2; on match, issues an access token

Why PKCE? Without it, an attacker who intercepts the redirect (malicious app on the device, misconfigured redirect handler) could exchange the auth code themselves. PKCE binds the code exchange to whoever generated the verifier — only they can complete it.

§10

WebAuthn / Passkeys

Public-key authentication baked into the browser. On registration, the user's device generates a fresh key pair specific to that site, stores the private key in secure hardware (TPM, Secure Enclave, hardware key), and sends the public key to the server. On login, the server sends a challenge; the device signs it with the private key; the signature is verified server-side against the stored public key.

Why it structurally ends phishing — three reasons:

  • The browser binds the signing operation to the actual origin of the page making the request. A phishing site at раypal.com simply cannot ask the authenticator for a signature meant for paypal.com. It's not "hard," it's impossible — the browser refuses.
  • There is no shared secret stored on the server. A database breach leaks public keys — useless to an attacker.
  • The user can't be tricked into revealing the credential, because there's nothing to reveal — it never leaves the secure hardware.

Passkeys are the consumer-friendly name. Apple, Google, Microsoft, and 1Password sync them via cloud accounts. The user experience is "use Face ID to log in." Server-side libraries: @simplewebauthn/server, fido2-lib.

§10

Five rules

  1. Never trust user data. Validate at the trust boundary; escape on the way out.
  2. Complexity is the enemy of security. Reach for boring, well-tested libraries.
  3. Be explicit, fail fast. Reject invalid requests before any business logic runs.
  4. Stack defenses. Assume each layer will be breached someday; bound the blast radius.
  5. Pay attention to defaults. The web's defaults are improving (SameSite=Lax, CSP, passkeys) — use them.
