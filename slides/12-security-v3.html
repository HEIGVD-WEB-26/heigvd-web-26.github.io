It's illegal

Don't pick at a site unless explicitly allowed.

  • CFAA (US): up to 20 years, applies to non-US citizens
  • Art. 143bis CP (CH): equivalent offense
  • Bug Bounty programs (HackerOne, Bugcrowd) are the legitimate way
Even researching a vulnerability on a system you don't own can be illegal. Bug bounty programs give you written authorization. Don't poke at random sites.

Same-Origin Policy

Page APage BSame?
http://a.comhttps://a.comNo (protocol)
https://a.comhttps://a.com:8443No (port)
https://a.comhttps://api.a.comNo (host)
https://a.comhttps://a.com:443Yes (443 is default)
  • Origin = (protocol, host, port)
  • Any one differs → different origin
  • Default ports (80, 443) are implicit
§2
Two pages from different origins can't read each other. Most common gotcha: developers forget that http and https are different origins.

SOP — what's blocked, what's allowed

  • Blocked: DOM access via iframe, fetch response body, reading cookies / localStorage
  • Allowed: embed <img>, <script>, <link>; form action
  • Opt-in cross-origin: postMessage for iframe comms, CORS for fetch
§2
Note that "blocked" usually means the browser hides the response from JS — the request still reaches the network. Side-effects on the server still happen. CORS protects the user, not the server.

Cross-origin via postMessage

// Child
window.addEventListener("message", (event) => {
  if (event.origin !== "https://parent.example.com") return;
  // use event.data
});
  • Always verify event.origin
  • Always pass a specific targetOrigin
  • Never use "*" for sensitive data
§2
Forgetting the origin check is the classic postMessage bug — any page that embeds yours can send commands. Pair this with frame-ancestors CSP to control who can embed you.

CORS

// JS at app.com tries to fetch api.com
fetch("https://api.com/data")

// Server response must include:
Access-Control-Allow-Origin: https://app.com
  • Enforced by the browser, not the server
  • Opt-in via response headers
  • Without headers → browser hides the response body
§3
The request still goes through and may have side effects! CORS is a defense against client-side JS exfiltrating data, not against attacks on your server. For that you need real auth / CSRF tokens / etc.

CORS — preflight

OPTIONS /api/account HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: X-Auth

HTTP/1.1 204 No Content
Access-Control-Allow-Methods: DELETE, GET
Access-Control-Allow-Headers: X-Auth
  • Triggered by non-simple methods (PUT/DELETE), custom headers, JSON content-type
  • Browser asks "may I?" before the real request
  • Server replies with the allow-list, then the real request goes
§3
Simple GET/HEAD/POST with form-encoded bodies skip the preflight — the browser sends them and just hides the response. That's why "doesn't change state on GET" is so important.

CORS — credentialed requests

fetch("https://api.com/me", { credentials: "include" })

// Server must respond:
Access-Control-Allow-Origin: https://app.com  ← specific, not *
Access-Control-Allow-Credentials: true
  • Cookies and HTTP auth are NOT sent cross-origin by default
  • Need credentials: "include" on the client
  • Need specific origin + Allow-Credentials on the server
§3
The wildcard Access-Control-Allow-Origin is invalid with credentials — it must be a specific origin. Common config mistake.

Cookies — anatomy

Set-Cookie: session_id=eyJhb...;
            Domain=example.com; Path=/;
            Max-Age=86400;
            Secure; HttpOnly; SameSite=Lax
  • Single key-value pair + attributes
  • Browser sends back with every request to the origin
  • Server controls; browser stores and forwards
§4
Cookies are how stateful sessions work on a stateless protocol. The attributes are where security lives — every one of them matters.

Cookies — security attributes

  • Secure — only sent over HTTPS (defeats network eavesdropping)
  • HttpOnly — invisible to JS (mitigates session theft via XSS)
  • SameSite=Lax — modern browser default; blocks naked CSRF on POST
§4
Strict, Lax, None: Strict never sends on cross-site, Lax sends on top-level GET, None sends on everything (requires Secure). Lax has been the default since 2020 in Chrome.

Cookie name prefixes

Set-Cookie: __Host-session=eyJ...;
            Secure; HttpOnly; SameSite=Lax;
            Path=/
  • __Secure- — must be set with Secure attribute
  • __Host- — must be Secure + Path=/ + no Domain (host-bound)
  • Use __Host- for session cookies
§4
The browser enforces the constraints based on the name prefix — it'll refuse to set a __Host- cookie that doesn't satisfy the rules. Free security.

Session IDs

  • Generate from a CSPRNG (crypto.randomBytes(32)) — never sequential
  • Rotate on login and on privilege escalation
  • Expire idle sessions server-side, not just by cookie Max-Age
§4
If I steal your session ID, I am you. Rotation on login defeats fixation attacks. Server-side expiry means an old leaked cookie eventually stops working even if its Max-Age says otherwise.

CSRF — classic

<!-- evil.com -->
<form action="https://bank.com/transfer" method="POST">
  <input name="to"     value="attacker">
  <input name="amount" value="1000">
</form>
<script>document.forms[0].submit()</script>
  • Cookies travel regardless of who triggered the request
  • Victim clicks "win iPad" → bank transfer happens
  • Pre-2020 this was an everyday bug
§5
The user is logged into bank.com. The form submits to bank.com, browser dutifully sends the session cookie. If the bank trusts session-cookie-alone, the transfer succeeds.

CSRF — modern view

  • SameSite=Lax is now the default (Chrome 2020+)
  • Closes naked CSRF on cross-site POST
  • Top-level GET still ships the cookie → never put state changes on GET
§5
The default fix closed most CSRF in one stroke. But you can't rely on every browser having it (old browsers, intranets). And destructive GET endpoints stay exposed under Lax.

CSRF — defense in depth

<form action="/transfer" method="POST">
  <input name="amount" value="1000">
  <input type="hidden" name="csrf"
         value="eyJ2IjoxLCJldSI6MCwic3QiOjB9">
</form>
  • Per-session secret token in hidden input
  • Server rejects state-changing requests without it
  • Double-submit cookie: stateless variant (token in cookie + header)
§5
The attacker can't read the token from another origin (SOP). Note: CSRF tokens don't protect against XSS — once attacker JS runs on your origin it can read the token.

XSS — three flavors

  • Reflected — URL contains payload, server echoes it back (1 click = 1 victim)
  • Stored — payload persisted in DB (every viewer hit)
  • DOM-based — client JS reads untrusted input, writes it as code
§6
XSS is the most common web vulnerability in study after study. Defenses are well-understood but easy to get wrong.

XSS — reflected example

// Server:
res.send(`<h1>Hello, ${req.query.user}</h1>`)

// URL the attacker sends:
?user=<img src=x onerror=alert(1)>
  • User input becomes executable code on the victim's browser
  • <img onerror> works even when <script> is filtered
  • Attacker code runs with the victim's origin and session
§6
With the user's session, the attacker can do anything the user could — read inbox, transfer money, change password. innerHTML refuses to execute script tags but happily runs onerror handlers — common gotcha.

XSS — three pillars of defense

  1. Escape on the way out, per context — template engine does it
  2. CSP with nonces — script-src 'self' 'nonce-…'
  3. Trusted Types — structural fix for DOM-XSS
§6
Escaping rules differ per context: element body, attribute value, JS string, URL. Wrong escape is silently insecure. CSP nonces stop injected inline scripts from executing because they don't have the nonce. Trusted Types makes innerHTML refuse raw strings — Chromium-stable.

Phishing — IDN homograph

https://www.аpple.com/

  • Cyrillic а (U+0430) ≠ Latin a
  • Browser shows punycode (xn--pple-43d.com) when scripts mix
  • Subdomain confusion is also rampant: apple.com-login.evil.com
§7
IDN abuse is mostly handled by browsers now, but exact-script lookalikes still slip through. Users skim — they don't read the URL carefully. Visual cues alone can't solve this.

Phishing — what actually helps

  • Password managers won't autofill on a wrong domain
  • Passkeys are bound to the origin → unphishable by design
  • User training: documented but modest, decays without reinforcement
§7
Phishing is fundamentally a people problem (Schneier). The platform-layer answer is binding credentials to origins — which password managers approximate and passkeys nail.

Server-side — SQL injection

// Vulnerable
db.query(`SELECT * FROM users
  WHERE name = '${user}' AND pass = '${pass}'`)

// Bypass: name = admin' --
//   → strips the AND pass clause
  • String-concatenated SQL → injection
  • Fix: parameterized queries (driver substitutes safely)
  • ORMs do this for you, with the bonus of types
§8
Classic, never goes away. The fix is one line — but you have to know to write it that way every time. ORMs reduce the surface; raw SQL means every query is a chance to mess up.

Server-side — SSRF

// Attacker submits:
{ "avatar_url":
  "http://169.254.169.254/latest/meta-data/..." }

// Your code:
const img = await fetch(req.body.avatar_url);
// → server fetches AWS metadata service
  • Your server is on the internal network — attacker isn't
  • Allowlist hosts, or validate the resolved IP isn't private
  • Beware DNS rebinding — re-resolve before connecting
§8
Capital One was a major SSRF breach. Image proxies, webhook delivery, PDF rendering, URL previews — all common SSRF entry points.

Server-side — supply chain & rate limiting

  • Supply chain: dependency confusion, typosquatting, maintainer compromise
  • Pin versions (lockfile), audit (npm audit, Dependabot, Renovate)
  • Rate-limit everything — credential stuffing, scraping, denial-of-wallet are mass-volume
§8
Supply chain is the rising attack class — recent npm package compromises hit major projects. Lockfiles + automated audit + minimal direct deps cut the surface. Rate limits aren't glamour but are first-class defense.

Storing passwords

  • Hash, don't encrypt (encryption is reversible)
  • Salt: random per-user, defeats rainbow tables
  • Slow function: bcrypt / scrypt / Argon2id (~100ms per hash)
§9
Don't roll your own — use the library. Bcrypt cost tuned so legitimate login is fast enough for users (~100ms) but brute-force is painful (100ms × billions of guesses).

Modern password rules (NIST SP 800-63B)

  • No forced periodic rotation (encourages weak, sequential passwords)
  • No silly composition rules — length beats complexity
  • Block known-breached passwords (HIBP k-anonymity API)
§9
Forced 90-day rotation pushes users to Spring2026! → Summer2026!. Allow long passwords (64 chars) and spaces. Rate-limit failed attempts. Never email or SMS passwords. Use 2FA / passkeys where it matters.

Auth mechanisms

StateRevokePhishing-proof?
Session cookieServer-sideEasyNo
JWT bearerStatelessHardNo
OAuth2 + PKCEToken-issuerIssuer's jobNo
WebAuthn / PasskeysPublic keysEasyYes
  • Session cookie: simple, easy to revoke, needs a shared store at scale
  • JWT bearer: stateless and nice for fleets — but revocation is hard
  • WebAuthn / Passkeys: the only structurally unphishable option
§10
Choose based on revocation needs, scale, and threat model. For new apps in 2026, passkeys for users + JWT for service-to-service is a common combo.

JWT — what's actually in one

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9     ← header
  .eyJzdWIiOiJhbGljZSIsInJvbGUiOiJ1c2VyIn0  ← payload
  .K7rL3p…signature…                       ← signature
  • 3 base64url parts: header.payload.signature
  • Payload is readable (signed, not encrypted) — never put secrets in it
  • Foot-guns: alg: "none", algorithm confusion (HS vs RS)
§10
Always pin the expected algorithm server-side — don't trust the alg field in the token's header. High-profile breaches have come from libraries that switched algs based on what the token claimed.

WebAuthn / Passkeys

  • Per-site keypair stored in secure hardware (TPM / Secure Enclave / hardware key)
  • Browser binds the signature to the actual origin → ends phishing
  • Server stores only public keys → a breach reveals nothing usable
§10
Apple, Google, Microsoft, 1Password sync passkeys via cloud accounts. User experience is "use Face ID to log in." Server libraries: @simplewebauthn/server, fido2-lib.

Five rules

  1. Never trust user data
  2. Complexity is the enemy of security
  3. Be explicit, fail fast
  4. Stack defenses
  5. Use the platform's good defaults
