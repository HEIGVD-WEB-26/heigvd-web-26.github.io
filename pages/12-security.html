Preface

It's illegal

Unless you have explicit permission from the owner of a website, you may not pick at it. In the US this is a violation of the Computer Fraud and Abuse Act (CFAA) and can carry up to 20 years in prison; it applies to non-US citizens too. In Switzerland the equivalent is Art. 143bis CP.

If you want to practice on real systems, go on a Bug Bounty program where the owner has signed up to be tested.

Vocabulary: crypter vs chiffrer

  • Chiffrer: transform a message into an unreadable one using a key. Reversible with the key.
  • Déchiffrer: reverse the operation using the key.
  • Décrypter: reverse the operation without the key (i.e. break the cipher).
  • Crypter: does not exist in French. Use chiffrer.

Threat map

Web applications span three layers, and each layer is its own attack surface:

LayerWhat lives hereAttack classes covered in this chapter
BrowserYour HTML, JS, cookies, the user's sessionSOP violations, XSS, CSRF, phishing
NetworkHTTP between client and serverCORS misconfiguration, eavesdropping (HTTPS / HSTS)
ServerYour code, your database, your dependenciesSQL injection, SSRF, info leaks, supply chain, weak password storage

The rest of the page walks each layer top-down. A recurring assumption: the attacker can send any bytes to your server, and can run any code on their own browser — the security model lives at the boundaries.

Same-Origin Policy

Rule: two pages from different origins should not be able to interfere with each other. An origin is the triple (protocol, host, port). Any one of those differing makes it a different origin.

What counts as interference

  • Reading or modifying the DOM of another page (e.g. via an iframe's contentDocument)
  • fetch from another origin (response body is hidden by default)
  • Reading another origin's cookies, localStorage, IndexedDB

Exceptions (intentional cross-origin)

  • Embedded static resources: <img>, <script>, <link rel="stylesheet">
  • Form action: <form action="https://otherserver.com"> is allowed
  • postMessage for explicit, opt-in cross-origin communication

iframe communication via postMessage

The legitimate way for an embedder and its iframe to talk:

// Embedder
iframe.contentWindow.postMessage(msg, "https://child.example.com");

// Child
window.addEventListener("message", (event) => {
  if (event.origin !== "https://parent.example.com") return;
  // ... use event.data
});

Always verify event.origin and pass a specific targetOrigin, never "*".

document.domain is dead

Historically, pages on different subdomains of the same parent (app.example.com and www.example.com) could opt in to scripting each other by both setting document.domain = 'example.com'. As of Chrome 115 (2023) this no longer works — setting document.domain is a no-op. Use postMessage across origins instead.

Preventing your page from being embedded

Use Content-Security-Policy: frame-ancestors 'none' (modern) or the legacy X-Frame-Options: DENY.

Practice

Two origins or not? http://www.example.com vs http://www.example.com:80.

Same origin. Port 80 is the default for http; the omitted port is implicitly 80.

Two origins or not? https://example.com vs https://example.com:443.

Same origin. 443 is the default port for https.

Two origins or not? https://example.com vs https://api.example.com.

Different origins. The host differs (example.com vs api.example.com).

CORS — Cross-Origin Resource Sharing

The Same-Origin Policy blocks most cross-origin requests by default. CORS is the opt-in mechanism that lets a server selectively allow them. CORS is enforced by the browser, not the server — the response still reaches the network, the browser just refuses to give it to your JS.

Simple requests

A request is "simple" (no preflight required) if it uses GET, HEAD, or POST, with a small set of headers and content types. The browser sends the request; the server's response must include:

Access-Control-Allow-Origin: https://your-app.example.com

If the header is missing or doesn't match, the browser hides the response body from JS.

Preflight (non-simple) requests

For PUT, DELETE, requests with Content-Type: application/json, or custom headers, the browser first sends an OPTIONS request:

OPTIONS /api/account HTTP/1.1
Host: api.example.com
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: X-Auth, Content-Type

The server responds with the allow-list:

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: DELETE, GET
Access-Control-Allow-Headers: X-Auth, Content-Type
Access-Control-Max-Age: 600

Only then does the browser send the real DELETE.

Credentialed requests

Cookies and HTTP auth are NOT sent cross-origin by default. To include them, set credentials: "include" on fetch — and the server must respond with Access-Control-Allow-Credentials: true AND a specific (non-wildcard) Access-Control-Allow-Origin. Either missing → the browser drops the response.

Practice

A JS app at https://app.com calls fetch("https://api.com/data"). The server responds 200 with the data but no CORS headers. What does the app see?

The fetch Promise rejects with a CORS error. The server received the request and processed it (potentially with side effects!), but the browser refused to expose the response to the app's JS.

Same app sets credentials: "include". Server responds with Access-Control-Allow-Origin: * and Access-Control-Allow-Credentials: true. Does it work?

No. With credentials, Allow-Origin: * is invalid — it must be a specific origin. The browser drops the response.

Cookies and Sessions

Cookies are small key-value pairs the server tells the browser to store; the browser sends them back on every subsequent request to that origin. They are how the web does state across HTTP's stateless model.

Anatomy

Set-Cookie: session_id=eyJhb...; Domain=example.com; Path=/; Max-Age=86400;
            Secure; HttpOnly; SameSite=Lax

The attributes that matter for security

  • Secure — only sent over HTTPS. Without it, a network eavesdropper can steal the cookie.
  • HttpOnly — not readable from JS (document.cookie can't see it). Mitigates session theft via XSS.
  • SameSite — controls sending on cross-site requests:
    • Strict — never on cross-site requests (even clicking a link from another site).
    • Lax — sent on top-level GET navigation only. This is the modern browser default since 2020.
    • None — sent on every cross-site request (requires Secure).
  • Domain / Path — restricts which hosts/paths receive the cookie.
  • Max-Age / Expires — expiry. Missing both → session cookie (browser-defined lifetime).

Name prefixes — __Host- and __Secure-

Modern browsers enforce stronger guarantees if the cookie name starts with one of these prefixes:

  • __Secure-name — must be set with Secure attribute (i.e. only over HTTPS).
  • __Host-name — must be Secure, must have Path=/, must NOT have a Domain attribute (host-bound). Best choice for session cookies.

Partitioned (CHIPS)

Third-party cookies are being phased out. The Partitioned attribute (CHIPS — Cookies Having Independent Partitioned State) opts a cross-site cookie into the new partitioned model: the same session cookie set on widget.example.com when embedded on siteA.com is a different storage slot from the one on siteB.com. Required for legitimate cross-site embeds going forward.

Set-Cookie: __Host-session=abc; Secure; HttpOnly; SameSite=None; Partitioned

Sessions

A session ID is a server-issued random secret stored in a cookie. The server keeps the corresponding session state (logged-in user, cart, etc.) in memory or a database. If I steal your session ID, I am you — so:

  • Generate session IDs from a CSPRNG (e.g. Node's crypto.randomBytes(32)). Never sequential or guessable.
  • Set Secure; HttpOnly; SameSite=Lax (or Strict if your UX allows).
  • Use the __Host- prefix.
  • Rotate the session ID on login and on privilege escalation.
  • Expire idle sessions server-side, not just by the cookie's Max-Age.

CSRF — Cross-Site Request Forgery

Cookies travel with every request to their origin, regardless of who triggered the request. CSRF abuses this: a malicious page tricks the user's browser into firing an authenticated request to a target site where the user already has a session.

Classic example

<!-- on evil.com -->
<form action="https://bank.com/transfer" method="POST">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="1000">
  <input type="submit" value="Click here to win a free iPad!">
</form>
<script>document.forms[0].submit();</script>

If the user is logged into bank.com and the bank's transfer endpoint trusts the session cookie alone, the transfer succeeds.

How much does the modern default fix?

Most browsers now default to SameSite=Lax for cookies without an explicit attribute. That alone closes naked CSRF for POST and non-simple methods: the cookie simply isn't sent on a cross-site POST. Top-level GET navigation still ships the cookie under Lax — so if your endpoint takes destructive action on GET (it shouldn't), you are still exposed.

Defense in depth — when you still want a token

If you support cross-site embeds, third-party SSO, or you can't trust every browser to enforce SameSite=Lax (older browsers, intranet zones, etc.), add a CSRF token:

  • Server generates a per-session secret token, embeds it in forms as a hidden input.
  • Server rejects state-changing requests unless the submitted token matches the session's token.
  • An attacker on another origin can't read the token (SOP), and can't guess it.

Pattern variant: double-submit cookie — the same random value is sent both as a cookie AND as a request header; the server checks they match. Stateless on the server.

Referer vs Origin

  • Origin — the source's origin only (scheme + host + port). Sent on all non-GET cross-origin requests.
  • Referer — full URL of the page that initiated the request. Useful for analytics/logging; can be stripped or omitted by the user or by referrer policy, so don't make security decisions on it alone.

Practice

A site sets session=abc; Secure; HttpOnly (no SameSite attribute). User is logged in. Attacker's page does fetch("https://target.com/api/delete", { method: "POST", credentials: "include" }). Does the cookie travel?

No — modern browsers default missing SameSite to Lax, which blocks cross-site POSTs. (Older browsers without that default would send it — defense in depth still matters.)

Same site, same cookie, but the attacker tricks the user into clicking a link to https://target.com/api/delete?id=42. Does the cookie travel?

Yes — Lax allows top-level GET cross-site navigations. This is why state-changing operations must never be on GET, and why CSRF tokens are still useful.

XSS — Cross-Site Scripting

XSS is a code-injection vulnerability where untrusted user data becomes executable code on someone else's browser. It's the most common web vulnerability in study after study; defenses are well-understood but easy to get wrong.

Three flavors

  • Reflected — attacker crafts a URL whose query string is included unescaped in the server's response. Victim clicks the link, runs the code.
  • Stored — attacker submits content (a comment, profile field) that the server stores and later serves to other users unescaped.
  • DOM-based — vulnerable client-side JS reads untrusted input (URL, postMessage, fragment) and writes it into the DOM in a way that creates code.

Play with it — element body context

Below, a tiny vulnerable server reflects req.query.user into the HTML body. Try payloads:

  • <img src=x onerror=alert(1)>
  • <svg onload=alert(1)>
  • <script>alert(1)</script> — typically does NOT fire when inserted via innerHTML-style reflection, but DOES fire when reflected by the server's HTML response (try both).

Same vulnerability, different context — attribute value

If user input lands inside an HTML attribute (here, alt=…), the payload shape changes — you have to break out of the quoted attribute first.

Defenses, in layers

  1. Escape on the way out, per context. Use a template engine that does it for you (ejs <%= %>, React's {}, Vue). Never concatenate user input into HTML strings. The required escaping is different for element body, attribute value, JS string, URL — and using the wrong one is silently insecure.
  2. Content Security Policy. A CSP header restricts where scripts may load from and inlines what code can run. Modern best practice uses nonces or hashes: 
    Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m';
  object-src 'none';
  base-uri 'self';
    Every legitimate <script nonce="r4nd0m"> tag carries the nonce; injected scripts don't, so the browser refuses to run them.
  3. Trusted Types (Chromium-stable). Forces all DOM sinks like innerHTML, setTimeout(string), eval to consume only sanitizer-produced policy objects, not raw strings: 
    Content-Security-Policy: require-trusted-types-for 'script';
trusted-types my-policy;
    With this set, el.innerHTML = userString throws unless userString came from a registered sanitizer policy. Structurally prevents DOM XSS.
  4. Stack defenses. Assume XSS will eventually happen: HttpOnly cookies, re-authenticate for sensitive actions (password change, fund transfer), audit logs, sensible session timeout. Then if XSS does land, the blast radius is bounded.

The "escape into JS" trap

Escaping HTML inside a <script> block is not safe. There are two parsers (HTML, JS) and a payload like </script><script>alert(1)</script> breaks out of the script tag regardless of how you escape quotes. If you must pass server data to client JS, route it through an HTML container:

<template id="user-data">${htmlEscape(userJson)}</template>
<script>
  const data = JSON.parse(document.getElementById('user-data').textContent);
</script>

Variable injection (a sibling problem)

HTML elements with an id attribute create a global JS variable of that name. If a user-controlled value becomes an element's id, the attacker can shadow legitimate globals:

// Server reflects user-controlled displayName into the id attribute:
<div id="${userDisplayName}">...</div>

// If userDisplayName === "nextTimeout", a real global named nextTimeout
// is created — silently breaking code that expected its own variable.

Practice

Server code: res.send(`<a href="${userUrl}">Click</a>`). userUrl is HTML-escaped before reflecting. Is this safe?

No. HTML escaping leaves the payload javascript:alert(1) intact — and the browser executes JS URLs from href. Defense: URL-validate as well (e.g. reject anything not starting with https:// or /).

Are CSRF tokens a mitigation against XSS?

No. CSRF tokens stop other origins from forging requests. XSS runs on your own origin — the injected JS can simply read the CSRF token from the page and use it.

Phishing

"Security solutions have a technological component, but security is fundamentally a people problem." — Bruce Schneier

Phishing tricks the user, not the code. The web platform offers attackers several primitives for impersonation:

Internationalized Domain Names (IDN)

Hostnames may contain Unicode. They are encoded to ASCII as "punycode" for DNS. So xn--80ak6aa92e.com is what your browser sends; аррӏе.com is what the user reads — and the а is Cyrillic, the ӏ is not an l. Browsers now show punycode when characters mix scripts, but legacy and exact-script lookalikes still slip through.

Subdomain confusion

http://apple.com-webapps-userid29348325.active-userid.com/login

The actual domain is active-userid.com. Browsers help by greying out subdomains in the URL bar, but users skim.

UI fakery

  • HTML5 fullscreen API — pretend to be the OS.
  • The inception bar — render a fake address bar after scroll.

What actually helps

  • Password managers won't autofill on a wrong domain.
  • Hardware security keys / Passkeys are bound to the relying-party's origin and refuse to sign for any other site. This structurally ends phishing for the user. See the Auth section below.
  • User training has documented but modest impact and decays without continuous reinforcement.

Practice — spot the homograph

Is https://www.раypal.com the real PayPal?

No. The а is Cyrillic U+0430, not Latin a. Modern browsers show this as https://www.xn--paypal-c6f.com in the address bar. A password manager would refuse to autofill.

Server-side security

On the server, the attacker is no longer bound by your UI or by browser-enforced rules like SOP/CORS. They can send any bytes to any endpoint. The security model has to live in your server code.

SQL injection

String-concatenated SQL is the canonical bug. Below, the handler concatenates user input into the query — try the classic admin' -- trick:

The fix: parameterized queries. The driver sends the SQL and the values as separate things to the database; the database substitutes safely.

// Vulnerable
db.query(`SELECT * FROM users WHERE name = '${user}'`)

// Safe
db.query('SELECT * FROM users WHERE name = $1', [user])

An ORM (Prisma, Sequelize, Drizzle…) does this for you, with the side benefit of types.

SSRF — Server-Side Request Forgery

Your server is on the same network as services the public internet can't reach (a metadata service, an internal API). If your endpoint takes a URL from the user and fetches it (image proxy, webhook delivery, PDF rendering), the attacker can make your server hit those internal targets:

// Attacker submits:
{ "avatar_url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/" }

// Your code:
const img = await fetch(req.body.avatar_url);  // your server fetches AWS metadata

Defenses:

  • Allowlist hosts (e.g. only fetch from cdn.example.com).
  • If users supply arbitrary URLs, resolve the DNS yourself and verify the IP is public (not 127.0.0.1, 10.0.0.0/8, 169.254.169.254…). Beware DNS rebinding — re-resolve and re-check before the connect, or use a library that does both.
  • Set short connect timeouts and don't follow redirects without re-validating.

Information leaks

The server may give you the breach without an active attack:

  • Stack traces in error responses (database names, table names, file paths).
  • Over-fetching — returning the full user object when the client only needed the display name.
  • Verbose errors revealing whether a user exists (login, password reset, signup) — see Auth below for the response-discrepancy pattern.

Supply chain

Web apps load 100s of npm transitive dependencies — any of which can be compromised:

  • Dependency confusion — attacker publishes a package with the same name as your internal private one on the public registry; your build picks the public one.
  • Typosquatting — colorss, nodemon-cli, etc.
  • Maintainer compromise — legitimate package gets a malicious update pushed.

Defenses: pin versions (lockfile committed), audit (npm audit, Dependabot, Renovate), avoid postinstall scripts where possible, and consider runtime allowlists (e.g. --allow-net in Deno).

Rate limiting

Not glamour — but most online attacks (credential stuffing, scraping, denial-of-wallet on paid APIs) are mass-volume. Per-IP and per-account rate limits, with backoff and lockouts on failed auth, are a first-class defense, not a polish item.

Practice

A "fetch URL preview" endpoint accepts any HTTP URL. The dev plans to "block localhost and 127.0.0.1". Is that enough?

No. Loopback comes in many shapes — 0.0.0.0, [::1], 2130706433 (the integer form), 127.1, decimal/octal/hex variants, IPv6 mapped IPv4. And the private network ranges (10/8, 172.16/12, 192.168/16) and the link-local 169.254/16 are usually more dangerous than localhost. Allowlist hosts, or resolve DNS yourself and check the IP against a comprehensive private-range list.

Storing passwords

Don't encrypt — hash

Encryption is reversible: someone holds the key. If your host is compromised, the key likely is too. Hashing is one-way: a leaked database doesn't give the attacker passwords directly. But raw hashing is not enough:

  • Identical passwords produce identical hashes — patterns leak.
  • Precomputed rainbow tables crack common passwords for free.

Hash + salt + slow function

  • Salt — random per-user bytes, stored alongside the hash. Two users with the same password get different hashes; rainbow tables become useless.
  • Slow function — bcrypt, scrypt, Argon2id. Tuned so a single hash takes ~100ms on production hardware. The user logs in once; the attacker brute-forcing the leak pays 100ms per guess.
  • Use a library. Don't roll your own — there are many ways to get this subtly wrong.

Move the cost slider below — a cost of 4 is roughly 100× faster than a cost of 12. The defender picks the highest cost they can tolerate.

Other implementation rules (NIST SP 800-63B in one bullet list)

  • No mandatory periodic changes. Forced rotation pushes users toward weaker, sequential passwords ("Spring2026!" → "Summer2026!"). Rotate only on suspected compromise.
  • No silly composition rules (one uppercase, one symbol, …). Length beats complexity. Allow long passwords (min 64 chars), allow spaces.
  • Block known-breached passwords. Check candidate passwords against HIBP's k-anonymity API at signup and password change.
  • Rate-limit and lock out failed attempts. A bcrypt cost of 12 helps offline; rate limiting helps online.
  • Never send passwords by email or SMS. Use one-time signed links.
  • 2FA / MFA on anything important. Prefer WebAuthn/Passkeys over TOTP over SMS.

Auth mechanisms

Three things often called "auth"

  • Identification — claim who you are (a username).
  • Authentication — prove it (password, key, biometrics).
  • Authorization — given that you are X, are you allowed to do this?

The HTTP Authorization header

A standard header with a freely-chosen scheme. Common ones:

  • Authorization: Basic base64(user:pass) — only safe over HTTPS; ~plaintext.
  • Authorization: Bearer token — an opaque or signed token. JWT is a common token format.

Session cookie vs Bearer JWT

JWT — what's actually in one

Three parts separated by .: base64url-encoded header, base64url-encoded payload, signature over the first two.

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
  .eyJzdWIiOiJhbGljZSIsInJvbGUiOiJ1c2VyIn0
  .K7rL3p…signature…

JWT classic foot-guns:

  • alg: "none" — some libraries historically accepted unsigned tokens. Always validate alg against an allowlist on the server.
  • Algorithm confusion — server uses HS256, attacker sends RS256 (or vice versa), tricks the library into validating with the wrong key. Pin algorithm server-side.
  • Putting secrets in the payload — payload is base64, not encrypted. Anyone with the token can read it.

Play with one:

OAuth2 — Authorization Code with PKCE

OAuth2 lets a third-party app act on a user's behalf without seeing the user's credentials. The modern recommended flow for browser apps is Authorization Code + PKCE. Step by step:

  1. The app generates a random code_verifier, hashes it (SHA-256), base64url-encodes it → code_challenge.
  2. App sends the user to the authorization server: GET /authorize?response_type=code&client_id=…&code_challenge=…&code_challenge_method=S256&redirect_uri=…&state=…
  3. User logs in there, consents.
  4. Auth server redirects to redirect_uri?code=AUTH_CODE&state=….
  5. App's frontend receives the auth code; it now needs to exchange it for a token. It POSTs to the token endpoint with the original code_verifier: POST /token grant_type=authorization_code&code=AUTH_CODE&code_verifier=…&client_id=…
  6. Auth server hashes the verifier and checks against the challenge it stored in step 2. Match → it issues an access token (often a JWT).

Why PKCE? Without it, an attacker who intercepts the redirect (malicious app on the device, a misconfigured redirect) could exchange the auth code themselves. PKCE binds the code exchange to whoever generated the original verifier.

WebAuthn / Passkeys

Public-key authentication baked into the browser. On registration, the user's device generates a fresh key pair per site, stores the private key in secure hardware (TPM, Secure Enclave, hardware key), and sends the public key to the server. On login, the server sends a challenge; the device signs it with the private key. The signature is verified server-side.

Why it structurally ends phishing:

  • The browser binds the signing operation to the actual origin of the page making the request. A phishing site at раypal.com simply cannot ask the authenticator for a signature meant for paypal.com.
  • There is no shared secret to steal in a database breach — only public keys.
  • Passkeys (the consumer-friendly name) sync via iCloud / Google / 1Password; the user's experience is "use Face ID to log in."

Server-side, you store a public key per user. Libraries: @simplewebauthn/server, fido2-lib.

Practice

A JWT has {"alg":"HS256","typ":"JWT"} in its header. An attacker submits the same token with the header rewritten to {"alg":"none"} and an empty signature. What should the server do?

Reject it. The server's verifier must pin the expected algorithm — never trust the header's alg. Many high-profile breaches have come from libraries that accepted alg: none or that switched between HS/RS based on the header.

A breach dumps the server's user table. Which storage scheme is least bad: plaintext, AES-encrypted with the key in env vars, SHA-256(password), bcrypt(password)?

From worst to best: plaintext (instant compromise), SHA-256 (no salt, rainbow-table able, fast — crackable in seconds for common passwords), AES-encrypted (the key is in env vars on the same host — usually compromised too), bcrypt (offline attack still pays per-guess cost). With WebAuthn there's nothing usable in the dump at all — just public keys.

Takeaways & references

The five rules

  1. Never trust user data. Validate at the trust boundary, escape on the way out.
  2. Complexity is the enemy of security. Reach for boring, well-tested libraries.
  3. Be explicit, fail fast. Reject invalid requests before any business logic runs.
  4. Stack defenses. Assume each layer will be breached someday; bound the blast radius.
  5. Pay attention to defaults. The web's defaults are improving (SameSite=Lax, CSP, passkeys) — use them.
